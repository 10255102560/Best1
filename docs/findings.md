# 实测结论与作业讨论

本项目已经完成真实模型实验，而不是用模拟响应替代 benchmark。模型为用户指定的 `deepseek-v4.1-flash`；训练 128 题、验证 48 题、最终测试 128 题，均来自完整官方 GSM8K 数据池。训练/验证来自官方 train，最终测试来自官方 test。

## 1. 找到了什么问题

问题是固定 harness 的过度推理和无条件复核。对所有题目都展开计算或追加检查，可能增加开销，却不一定修复错误。

本次测试中，固定复核策略与原始分步推理都答对 123/128 题，但平均总 token 从 328.14 上升至 763.00，增加约 **132.5%**。复核纠正错误 0 次、改错正确答案 0 次；在这组观察中，复核没有提供额外正确答案。

这不是“复核永远没用”，只说明当前模型、题目与提示组合不值得无条件追加复核。

## 2. 如何用梯度解决

把可选执行流程限制为直接回答、分步推理、分步推理后复核。题面提取 15 维特征，用 48 参数 softmax 调度器选择流程。

每道训练题实际测量三条路线的正确率和完整 token 成本。目标是正确率减去 token 惩罚，加熵与 L2 正则；用精确期望梯度在 CPU 上更新参数。每轮处理新训练题，累积反馈，从现任版本暖启动更新，再通过验证集门禁决定是否接纳。

正式方案四轮各增加 32 道训练题，每轮 400 次梯度更新。前两轮未接纳，第三轮接纳，第四轮未改善；最终冻结第三轮版本。它在测试题上选择 direct 7 次、reason 121 次、review 0 次。

## 3. 实际收益与强基线

| 方法 | 测试正确数 | 正确率 | 平均总 token | 相对原流程 token 节省 |
|---|---:|---:|---:|---:|
| 原始固定分步推理 | 123/128 | 96.09% | 328.14 | — |
| 冻结梯度路由 | 123/128 | 96.09% | 322.00 | **1.87%** |
| 验证集选出的最佳固定流程：直接回答 | 124/128 | 96.88% | 245.20 | **25.28%** |
| 固定复核 | 123/128 | 96.09% | 763.00 | -132.52% |

梯度路由相对原始流程的每题 token 差为 **−6.14**，按题配对 bootstrap 的 95% 区间为 **[−11.47, −1.83]**。这支持本批数据下的小幅开销改善。两条流程在这批题目的逐题正确与错误完全相同；不能据此保证未来所有题目均无准确率损失。

相对最佳固定流程，梯度路由每题反而多用 **76.80 token**，效用差的 95% 区间为 **[−0.02879, −0.00284]**，因此不能声称复杂路由优于简单固定选择。直接回答多答对 1 题只是点估计，不把这一个样本的差异宣称为准确率显著提升。

**当前模型和基准下，实际部署更推荐验证集选出的固定直接回答。** 正式冻结的梯度路由仍保留在工程中，作为完整可复现的方法实验；不会把测试后推荐冒充原来部署的梯度版本。

## 4. 为什么复杂路由没有胜出

观察到的 oracle 上界也只答对 124/128 题，与固定直接回答相同。Oracle 平均 token 为 241.87，比直接回答的 245.20 只少 3.33，潜在的进一步节省约 **1.36%**。这里的 oracle 利用测试标签，不能部署，但可诊断这组三个动作几乎没有互补空间。

因此，最主要的经验是：在投入复杂路由之前，应先检查候选流程是否互有优劣。动作几乎被一种简单流程支配时，增加控制器复杂度可能只会增加估计误差。

400 步的代理目标更新也不一定足以让 argmax 改变。项目另存了一次 4,000 步的收敛诊断：在前 64 道训练题和同一验证集上，策略变成全 direct。该诊断未读取测试响应，但其冻结时间晚于正式测试请求开始，故严格列为**补充探索**，不作为原先冻结方案的确认性结果，也不宣称它具有超越固定 direct 的上下文路由能力。见 `artifacts/convergence_check/NOTE.md`。

## 5. 成本、边界和后续三天计划

主实验共尝试 **938 次请求**，其中 **912 次成功、26 次失败**；另有早期连通性探测 1 次，共 939 次，低于用户授权的约 1,000 次上限。主实验成功响应记录 **315,817 token**；连通性探测记录 78 token。失败请求可能存在无法从日志还原的供应商计费，不能将这些已知 token 总数称作完整账单。

服务端限流后增加了全局节流与冷却；截断且没有最终答案的有效响应按答错计分并保留 token 成本。修复发生在任何训练采集及最终测试之前，旧配置和说明保存在 `config_history/`，未更换题目或提示。

这是固定基础模型下的参数自适应 harness，不训练大模型，不修改任意工程代码，也没有证明开放式递归智能提升。只有一个模型、一个公开基准子集、一个训练种子和每动作一次有效采样；区间反映这组题目的抽样不确定性，不覆盖模型版本变化和公开题库污染。

若继续用三天扩展，可以安排：

1. 第一天：使用现有离线数据完成课程演示，介绍梯度推导、门禁与成本核算；复现失败与成功结果。
2. 第二天：在全新开发集引入确有互补性的任务，例如工具可验证的计算题、需要检索的题目，加入“调用计算器/检索”等有实质差异的动作；先测开发集上的 oracle 空间。
3. 第三天：冻结新版本，用从未用于当前探索的新测试集，与验证集最佳固定策略、成本感知启发式比较。只有此时才能把新的调参结论当作独立验证。

上述扩展尚未执行，当前交付只包含已记录的真实实验，未虚构额外收益。
